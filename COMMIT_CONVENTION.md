# Соглашение о сообщениях коммитов

В репозитории используется упрощённый формат Conventional Commits. Сообщение
коммита должно кратко описывать основное изменение и соответствовать формату:

```text
type(scope): краткое описание
```

Если scope не нужен, его можно опустить:

```text
type: краткое описание
```

## Правила

1. `type` обязателен и должен быть написан строчными буквами.
2. `scope` необязателен. Если он указан, его нужно писать в нижнем регистре,
   используя только латинские буквы, цифры и дефис.
3. После двоеточия ставится один пробел.
4. Описание пишется на русском языке и начинается с глагола прошедшего времени
   мужского рода: `добавил`, `исправил`, `обновил`, `убрал`, `переработал`.
5. Описание должно быть конкретным, не заканчиваться точкой и по возможности
   укладываться в 72 символа.
6. Один коммит должен содержать одно логически связанное изменение.

Каждое описание должно быть на русском языке. В одном коммите не следует
смешивать русские и английские формулировки без необходимости.

## Типы коммитов

| Тип | Когда использовать | Пример |
|-----|--------------------|--------|
| `feat` | Новая функциональность или заметное изменение поведения | `feat(game): добавил итог раунда` |
| `fix` | Исправление ошибки | `fix(ui): исправил состояние кнопки выбора` |
| `docs` | Документация и комментарии | `docs: обновил описание задания` |
| `style` | Изменение внешнего вида или форматирования без изменения логики | `style(ui): скорректировал отступы выбора` |
| `refactor` | Перестройка кода без изменения поведения | `refactor(game): вынес обработку выбора` |
| `test` | Добавление или изменение тестов | `test(game): добавил варианты исхода раунда` |
| `chore` | Технические и вспомогательные изменения | `chore: реорганизовал публичные ресурсы` |
| `perf` | Оптимизация производительности без изменения поведения | `perf(ui): уменьшил число обновлений курсора` |

Не следует использовать `feat` для изменения только CSS или форматирования:
для таких изменений подходят `style` или `refactor`, в зависимости от сути.

## Допустимые scope

Используйте scope только тогда, когда он действительно уточняет область
изменений:

| Scope | Область |
|-------|---------|
| `game` | Игровая логика и состояние игры |
| `ui` | Разметка и взаимодействие с интерфейсом |
| `style` | CSS и визуальное оформление |
| `assets` | Изображения, шрифты и другие файлы в `public/` |
| `docs` | README, TASK и другие документы |
| `config` | Настройки и служебные файлы проекта |

Для изменений, затрагивающих несколько областей, можно не указывать scope,
если невозможно выбрать один основной.

## Примеры для этого проекта

```text
feat(game): добавил генерацию выбора компьютера
feat(ui): подключил кнопки выбора к игровой логике
fix(game): сбросил счёт при начале новой игры
fix(ui): убрал повторную анимацию выбора
style(ui): обновил разметку карточки выбора
refactor(game): вынес логику раунда в отдельную функцию
docs: уточнил правила игры в README
chore(assets): добавил иконки выбора
```

## Некорректные сообщения

```text
добавил новую функцию
```

Нет `type` и описание не передаёт конкретное изменение.

```text
Feat(ui): добавил кнопки
```

`type` должен быть в нижнем регистре.

```text
feat(ui)добавил кнопки
```

После двоеточия отсутствует пробел.

```text
fix: исправил
```

Описание слишком общее и не объясняет, что именно исправлено.

```text
feat(api): добавил конечную точку
```

В проекте нет API, поэтому такой scope и описание не соответствуют изменению.

## Перед созданием коммита

Проверьте, что:

- в коммит не попали временные файлы и файлы редактора;
- изменение относится к заявленной задаче;
- сообщение можно понять без просмотра diff;
- для связанных изменений использованы одинаковые формулировки.

В репозитории не настроен автоматический `commit-msg` hook, поэтому соблюдение
этого соглашения проверяется при ревью. Если проверка сообщений потребуется
позже, её следует добавить отдельно вместе с правилами CI или hook.
